# 피드백 리포트 — dev-base를 쓰는 머신·repo에서 개선 근거 남기기

dev-base 설정을 실제로 쓰면서 생긴 마찰·사용 흔적·누적물을 소유자 동의 하에 리포트로 남긴다. 리포트는 dev-base 개선(규칙·템플릿·절차·정리 규약)의 근거로만 쓴다.
아무 머신, 아무 harness의 역할 없는 세션에서 실행한다. 마찰이 생긴 프로젝트 세션에서 바로 해도 되고, `UPDATE.md` 끝에서 해도 된다. 역할 세션(앨리스 등)에서는 하지 않는다.

쓰는 법: 세션에 "`<dev-base>/prompts/feedback-report.md` 보고 진행해"라고 한다. 세션은 코드블록 안을 지시로, 밖을 실행 조건으로 읽는다.

```
dev-base 피드백 리포트를 만들어줘. 리포트 파일 말고는 아무것도 바꾸지 않는다(읽기 전용). 이 파일이 있는 폴더를 `<dev-base>`라고 쓴다.
Windows면 pwsh 7 기준으로 바꿔 실행한다. `~`는 `$HOME`이다.

준비
1. `~/.config/machine-context/local.md`가 있으면 읽고 실행 제약을 따른다. 머신 별칭(예: wsl-main, gs-zero)이 거기 없으면 나에게 묻고, local.md에 적을지 묻는다. 서버 역할이 드러나는 별칭(nas 등)은 피한다.
2. 대상 프로젝트를 정한다. local.md에 대상 프로젝트 목록(이름·경로)이 있으면 그것을 기본으로 제시하고, 없으면 나에게 묻는다(현재 작업 디렉터리가 프로젝트면 후보로 제시). 홈 전체를 탐색하지 않는다. 정한 목록을 local.md에 적을지 묻는다. dev-base 자체만 대상이어도 된다.

수집 (내용 원문을 통째로 옮기지 않는다. 메타 정보와 1~2줄 인용만)
3. 환경: 머신 별칭, OS, 이 세션의 harness·모델, 설치된 다른 harness(있으면 버전), `<dev-base>`와 그 아래 각 repo의 `git rev-parse --short HEAD`·`git status -sb` 첫 줄, `~/.config/agent-rules/three-man-team/SOURCE`의 `commit=`. 마지막 UPDATE 날짜·결과는 local.md에 기록이 있으면 쓰고 없으면 나에게 묻는다(모르면 "unknown").
4. 마찰: 이 세션에서 겪은 것 + 나에게 물어 받은 것. 항목마다 (무엇을 하려 했나 / 어떤 지침·절차·도구가 / 어떻게 막거나 어긋났나 / 어떻게 우회했나 / 근거 파일:줄)을 적는다. 종류: 지침 충돌, 지켜지지 않거나 우회된 규칙, 반복해서 다시 지시해야 했던 것, 절차 문서와 실제의 불일치, 불필요하게 비싼 단계.
5. 사용 흔적: 이 세션과 내 답에서 확인되는 범위만. 실제로 로드·사용한 스킬, 역할, dev-base 절차(UPDATE·MIGRATE·WORKER·prompts/*). 확인 안 되는 것은 "unknown"으로 두고 추측하지 않는다. 세션 로그 파일은 뒤지지 않는다.
6. 누적물 목록 (대상 프로젝트마다, 읽기만): `handoff*/`, `docs/`, `.tmt/`, 루트의 `*.md` 중 역할·지침 파일을 제외한 것, 그리고 1MB 이상인 git-ignored 폴더(`git status --ignored --porcelain`의 `!!` 디렉터리; `node_modules`·빌드 산출물·venv는 제외).
   - 집계 단위: 폴더(하위 폴더 포함)마다 한 줄 — 파일 수, 총크기, 미추적 수, 참조 0 수(파일명을 다른 추적 파일이 `git grep -l <basename>`으로 참조하지 않는 수), 수정일 범위. 파일이 20개를 넘는 폴더는 하위 폴더나 파일명 접두사(첫 `-`·`_`·`.` 앞)별 개수를 덧붙인다. 파일 단위 표는 쓰지 않는다.
   - 파일명을 적는 것은 관찰의 근거가 되는 파일뿐이다(참조 0인 추적 파일, 관례가 다른 파일 등).
   - 파일 내용은 읽지 않는다. 낡았는지 판정하지 않는다.
   - "관찰"은 필수다. 숫자 나열이 아니라 패턴을 적는다: 덮어쓰기 대신 쌓이는 곳, 프로젝트마다 다른 관례(아카이브 방식, handoff 추적 여부), handoff에 섞인 데이터, 중복 사본, 가장 빨리 커지는 곳.
7. 제안: 내가 말한 것과, 4~6에서 근거가 있는 것만. 근거 없는 일반론은 넣지 않는다.

작성
8. `~/.config/dev-base-feedback/<YYYY-MM-DD>-<머신 별칭>.private.md`에 쓴다(폴더 없으면 만든다). 같은 이름이 있으면 덮지 말고 `-2`, `-3`을 붙인다. 형식:
   # dev-base feedback — <date> <머신 별칭>
   ## 환경 / ## 마찰 / ## 사용 흔적 / ## 누적물 / ## 제안 / ## 처리
   `## 처리`는 비워 둔다(처리 세션이 채운다). 비밀값(토큰·비밀번호·키·쿠키)은 어떤 경우에도 넣지 않는다. 발견하면 `[secret]`로 적는다.
9. 리포트 전문을 보여주고 고칠 곳·뺄 곳을 묻는다. 반영 후 다시 보여준다.

public 파생본 (내가 요청할 때만)
10. 같은 이름의 `.public.md`를 원본에서 만든다. 원본은 고치지 않는다. 마스킹:
    - 호스트명·IP·포트·도메인·사용자명 → `[host]` 등 종류 표기
    - 회사·고객 repo 이름 → 별칭(`work-a`, `work-b`). 어느 repo가 회사 것인지 모르면 나에게 묻는다
    - 홈 아래 절대경로 → `~/…`, 프로젝트 내부 경로는 회사 repo면 디렉터리 한 단계까지만
    - 인용 → 회사 repo 인용은 삭제하고 요지만, 개인 repo 인용은 유지
    원본과의 diff를 보여주고 승인받는다. public 위치(dev-base·claude-settings-example 이슈 등)에는 `.public.md`만 올린다.

전송은 하지 않는다. 파일 경로만 보고하고 끝낸다.
```

## 원격 수집 (다른 머신을 ssh로)

그 머신에서 세션을 열 수 없을 때만 쓴다. 가능하면 그 머신 세션에서 실행한다 — 마찰·사용 흔적은 그 머신 세션만 안다.

- 읽기 전용, 위 3·6단계(환경·누적물)만 수집한다. 4·5단계(마찰·사용 흔적)는 나에게 물어 받은 것만 적고, 나머지는 "unknown"으로 둔다.
- 비대화형 ssh는 PATH가 비어 node·harness를 못 찾을 수 있다. `bash -ic '<cmd>'`로 감싼다.
- 대상 경로는 그 머신 local.md의 목록을 먼저 읽는다(`ssh <host> cat ~/.config/machine-context/local.md`).
- 파일명은 `<YYYY-MM-DD>-<머신 별칭>-remote.private.md`. 리포트 첫 줄 아래에 "원격 수집: <수집한 머신>에서 ssh"를 적는다. 같은 날 그 머신의 on-host 리포트가 생기면 이 파일의 `## 처리`에 "on-host 리포트로 대체"를 적고, on-host에 없는 관찰만 처리 때 병합한다.

## 전송·처리 (소유자)

- 전송: 수동. 다른 머신의 리포트는 처리할 머신의 `~/.config/dev-base-feedback/`로 옮긴다(scp, 클라우드 드라이브, 복사 붙여넣기 무엇이든). `.private.md`는 private 경로로만 옮긴다.
- 처리: dev-base 역할 없는 세션에서 "`~/.config/dev-base-feedback/`의 미처리 리포트(`## 처리`가 빈 것)를 분류해줘"라고 한다. 항목을 SETUP.md의 의존 방향대로 나눈다: 규칙·템플릿 문구 → claude-settings-example 이슈, 역할 템플릿 → 포크(claude-settings-example 경유), CLI 계약 → tmt-cli, 머신 절차 → dev-base. 반영·보류·기각과 링크를 각 리포트 `## 처리`에 적는다.
- 정리 규약(누적물 보존·삭제 기준)은 리포트가 여러 머신에서 쌓인 뒤 `## 누적물`을 근거로 정한다.
